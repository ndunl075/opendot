| # | Severity | Finding | Disposition |
|---|---|---|---|
| F1 | High | The chat WebSocket required an `Authorization` header, which browser JavaScript cannot set. | **Fixed.** The WebSocket also accepts the token as an offered subprotocol (`["opendot", "opendot.bearer.<token>"]`). The server selects `opendot` and never echoes the token. Because CORS does not cover WebSockets, the Origin header must be a local origin (127.0.0.1, localhost, [::1], or the Tauri shell), even with a valid token. Tests: `test_websocket_accepts_the_token_as_a_subprotocol`, `test_websocket_refuses_foreign_origins_even_with_the_token`, `test_local_origins_are_allowed`. A real-browser check runs with the UI in M3 (Playwright e2e, task 3.4). |
| F2 | High | The API escrowed approval tokens, but nothing connected the escrow to the loop's executor, and API tests used a fake loop. | **Fixed (round 1 found the first fix wired only in a test).** `agent/runtime.py` `build_agent_runtime` is the one production assembly. It wires API approve, then `TokenEscrow`, then `AgentLoop`, then `ApprovalGatedTools.run_approved`, then `ApprovalExecutor`, then `ActionExecutor` (the same idempotent boundary MCP and Telegram approvals use), plus the API app. M3 task 3.5 serves `runtime.app`. `tests/api/test_server_real_loop.py` builds the runtime through this factory: chat over HTTP, then the mid-tier review, then the approval card, then approve over HTTP, then exactly one Gmail draft and a completed task. A replayed approve returns 409 with no second draft; deny runs nothing. A test checks that the default executor is `ActionExecutor`. |
| F3 | High | `resume_all()` skipped approved `waiting_approval` tasks, and a restart lost the in-memory token, leaving the action stuck. | **Fixed.** `resume_all()` also runs waiting tasks whose approval was decided or has expired. Tokens are still never persisted (section 10). If an approval is `approved` but its token is gone, nothing was done, so the loop creates a fresh proposal and asks again. If it is `consumed` but the token is gone, the outcome is unknown, so the task is handed to the user with a "check it yourself" message rather than guessing. Tests: `test_f3_*` in `tests/agent/test_loop.py`. |
| F4 | High | Compaction sent a plan request between the budget check and the main request, without a second check (M1 F3 on this path). | **Fixed.** One `_preflight` (kill switch, plan-limit pause, provider feature switch, budgets, spend-spike check) runs immediately before every provider request: before compaction, and again after it before the main request. The model reviewer's request is also covered (F5). M1 F3 is resolved: every plan request made by the loop passes the daily hard stop. Test: `test_f4_budget_is_checked_again_after_compaction`. |
| F5 | High | The reviewer treated a 429 as a generic error, so no plan-wide pause was set and the card was shown without its review. | **Fixed.** The reviewer re-raises `UsageLimitExceeded`/`RateLimited` and budget errors. The loop sets the plan-wide pause (or the budget pause), and the tool step stays pending, so no approval card exists until the review has run. Other provider failures (for example unreachable) still leave a "reviewer model unavailable" concern on the card; the deterministic checks always run. Tests: `test_f5_reviewer_429_pauses_all_plan_requests_and_shows_no_card`, `test_a_429_propagates_so_the_loop_pauses_every_plan_request`, `test_budget_errors_propagate`. |
| F6 | High | A loop built without an injected reviewer had the model pass off, and the scenario harness disables it too. | **Fixed for the loop; the harness setting is accepted.** `AgentLoop` now builds a `Reviewer` with the registry, router and meter by default, so the mid-tier pass runs (test: `test_f6_default_reviewer_runs_the_mid_tier_model_pass`). The scenario harness keeps `use_model=False` on purpose. S1 to S10 assert exact provider call counts for the section 14 behaviors (for example S2: "the model was not called again while the task waits"), and none of the ten scenarios is about the reviewer. The model pass is covered by `tests/agent/test_reviewer.py` and the F5/F6 loop tests. |
| F7 | Medium | A specific `auto` rule could make sending or posting run without asking, though section 10 says ask every time. | **Fixed (refined in rounds 1 to 5; see F13 to F16).** `RuleEngine.decide` turns any `auto` outcome into a locked `ask` when `rules.defaults.is_send_or_post` says the intent reaches other people. That is true for the explicit send tools (`message_send_propose`, `gmail_message_send`, `github_pr_comment_create` ...), for any send verb (send, reply, post, publish, forward, invite, share ...), and for any non-read action on a message, comment or chat (create, schedule, update, edit, pin). It is false for local tools, the built-in read tools, read verbs (list, get, fetch, search ...), drafts, and mailbox-only changes inside mail apps. `always_allow` already refused send proposals. Tests: `test_send_and_post_ask_every_time_even_with_an_auto_rule` and `test_reads_drafts_and_events_are_not_sends`. |
| F8 | Medium | Restarting a `started` auto tool skipped `RuleEngine.decide()`. | **Fixed.** A restarted step goes through the full path again: tool-group check, rules, audit, kill switch and anomaly checks. It keeps the same `call_id` for the tool's idempotency. Test: `test_f8_restarted_tool_step_rechecks_the_rules` (a rule changed to `handoff` during the restart is honored). |
| F9 | Medium | Tool calls were not checked against the task's fixed tool group. | **Fixed.** A call to a tool outside the persisted group is refused before any rule is evaluated and reported back to the model. Test: `test_f9_tool_outside_the_task_group_is_refused`. |
| F10 | Medium | Paid providers could be used for chat or review without their feature switch (M1 F4). | **Fixed.** `providers.features.provider_allowed(use, provider, settings)`: the plan and a local model need only be enabled. A paid provider needs "Use Claude as the reviewer" for Anthropic reviews, and the paid-provider switch for chat; other paid reviewers are refused. The loop checks it in the preflight before every request, and the reviewer before its model pass. M1 F4 is resolved at the M2 callers; memory search is still off by default (section 9). Tests: `test_f10_paid_provider_needs_its_feature_switch`, `test_paid_reviewer_needs_its_feature_switch`. |
| F11 | Medium | `always_allow` matched `composio_execute`, but Composio proposals use `composio_tool_execute`. | **Fixed.** The mapping uses `composio.ACTION_TYPE`. The rules tests now build Composio approvals with the real type, so the deny-list refusal cases test what they claim. Test: `test_always_allow_uses_the_real_composio_action_type`. |
| F12 | High | (Round 1) Re-evaluating a crashed auto step could turn it into an `ask`. The new approval would carry a new idempotency key, so the action could run twice. | **Fixed.** A step that reached `started` (it may already have run) and now resolves to `ask` is handed to the user with a "check whether it happened" message. It is never proposed again. Round 2 found that a pause could reset such a step to `pending`; now a started step stays `started` until it is done. Tests: `test_f12_started_step_that_now_asks_is_handed_off_not_reproposed`, `test_f12_uncertainty_survives_a_pause_before_the_rerun`. |
| F13 | Medium | (Round 2) "chat" and "comments" forced `ask` on reads such as `GITHUB_LIST_ISSUE_COMMENTS`. | **Fixed.** Read verbs are checked first, so reads are never sends. Test: `test_reads_drafts_and_events_are_not_sends`. |
| F14 | High | (Round 3) `SLACK_CHAT_SCHEDULE_MESSAGE` and `SLACK_CHAT_UPDATE` escaped, because message nouns counted only together with a create verb. | **Fixed.** Any non-read action on a message noun counts as outgoing. When unsure, ask. |
| F15 | Medium | (Round 4) `GMAIL_MODIFY_MESSAGE` (labels, read state) counted as outgoing, so no rule could make routine inbox changes automatic. | **Fixed.** Mailbox-only changes (label, archive, star, mark, move ...) and Gmail's `modify` are not outgoing, unless a send verb is present. |
| F16 | Medium | (Round 5) The mailbox-only words were trusted in any app, so `GITHUB_MARK_DISCUSSION_COMMENT_AS_ANSWER` escaped. | **Fixed.** Mailbox-only words are trusted only when the tool or slug names a mail app (gmail, outlook, mail, email, imap). Elsewhere, an action on a message asks. The F7 test cases include this slug, `SLACK_PIN_MESSAGE` and `GMAIL_MODIFY_MESSAGE_AND_SEND`. |

**Residual risk, accepted.** `is_send_or_post` classifies unknown outside-app actions (mostly Composio slugs) by their words, and errs toward asking. A slug that sends with no send verb and no message noun could still be missed. The M4 connectors (task 4.4) declare for each tool whether it reaches other people, instead of relying on words. That task and the v0.1 security review (task 4.8) re-check this.
