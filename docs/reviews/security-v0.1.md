# OpenDot v0.1 security review

Reviewer: Sol (`gpt-6-sol`, effort xhigh, read-only) via `codex exec`, over `main` at commit `35d1f64` (all of M0 to M4 except the Connections setup UI, which a follow-up pass covered). This is ARCHITECTURE.md section 14, M4 task 4.8. Fixes by Opus (daemon and desktop) and Terra (UI, through Codex). Sol then re-checked every fix (see "Verification").

Threat model given to the reviewer: one user's own machine. Attackers: (a) any web page the user visits; (b) other local processes and other local users; (c) untrusted content the agent reads (emails, web pages, issues, documents) attempting prompt injection; (d) a compromised or malicious model response. Out of scope: someone at the unlocked machine, and supply chain beyond code fetched at runtime.

First verdict: not ready until S1 to S6. Verification round 1 found S1, S3, S4 and S5 only partly fixed and added S7 to S9. Round 2 found S1 and S3 still incomplete and added S10 and S11. Round 3 confirmed those and added S12; round 4 found S12 incomplete and added S13. Everything was then fixed (see "Verification").
Every finding is fixed or accepted with a reason.

| # | Severity | Finding | Disposition |
|---|---|---|---|
| S1 | High | The desktop app trusted any process answering on 127.0.0.1:8765 with a plausible 401, and then handed it the bearer token. Another local user could take the port first and capture the token. | **Fixed.** The access token never travels. `GET /v1/session/challenge?nonce=` makes the daemon prove it knows the token (HMAC of the client's fresh nonce) and hands out a single-use challenge. The client answers with HMAC(token, challenge) to `POST /v1/session` and gets a **session token**. The desktop app does this in one exchange (round 2: verifying and then sending the token separately left a race), and only the session token reaches the webview and the tray. Session tokens live only in the daemon's memory and die on every restart. Tests: `test_challenge_proves_the_daemon_and_the_client_without_sending_the_token`, `test_session_tokens_die_with_the_daemon`; the Rust code compiles in `pnpm -C desktop build`. |
| S2 | High | The web login cookie held the bearer token, and cookies are shared by every port on 127.0.0.1. A local process serving another loopback port could receive the cookie and use the API. | **Fixed.** No cookie at all. `/login` checks the pasted token against the API and keeps it in `localStorage` for exactly this origin (scheme, host and port), which another port cannot read. `/logout` removes it. No served page carries the token (`index.html` is public and secret-free), and the API never accepts cookies. The login and logout pages send a strict CSP and `frame-ancestors 'none'`. Tests: `test_no_cookie_ever_and_no_page_carries_the_token`, `test_api_needs_the_bearer_token_not_the_cookie`, plus UI tests for the token source order and the redirect to `/login`. |
| S3 | High | The data directory and SQLite database were created with default permissions, readable by other local users on a typical Linux setup. | **Fixed.** On POSIX the CLI sets a 077 umask at start, so everything OpenDot writes (database, WAL, logs, backups, token files) is owner-only. The desktop app creates its data folder 0700. The database layer creates its data directory 0700, tightens an existing OpenDot-owned folder to 0700, and tightens the database, WAL, SHM and journal files to 0600 on every connection; a folder the user chose for `--db` is left alone. If something readable by others cannot be made private, OpenDot refuses to open it (`InsecureDataError`) instead of carrying on (round 2). Windows profiles are already per-user. Tests: `tests/test_db_permissions.py` (Linux and macOS in CI), including `test_data_that_cannot_be_made_private_is_refused`. |
| S4 | High | A task's tool group was padded with unrelated tools, including writes that run without asking (for example `task_schedule`), so injected text in a calendar title could steer a compromised model into a write the user never asked for. | **Fixed.** Padding uses only tools the executor declares read-only (`McpTools.read_only_tools()`, from each tool's declared facts), and the production wrapper (`ApprovalGatedTools`) forwards that list (round 1). The filter applies to small tool sets too. A write tool is offered only when the request asked for it. Tests: `test_s4_unrequested_write_tools_are_never_offered`, `test_s4_the_production_wrapper_keeps_unrequested_writes_out`, `test_s4_small_declared_sets_are_filtered_too`. |
| S5 | Medium | `--token-file` was read without checking its owner or permissions. | **Fixed.** On POSIX the file is opened once without following symlinks, and owner, type and mode are checked on that same open file (`fstat`), so it cannot be swapped between check and read (round 1). It must be a regular file owned by the current user and not readable by group or others, and must hold a full-length token. Tests: `test_token_file_must_be_private_and_complete`, `test_token_file_symlink_is_refused_on_posix`. |
| S6 | Medium | Credit use was reported as "off" whenever OpenDot could not determine it, so onboarding accepted "credits off" without basis. Paid credits could then be spent past the plan allowance. | **Fixed.** `ChatGPTStatus.credits_enabled` is `true`, `false` or `null` (unknown); onboarding says plainly when OpenDot cannot check and still requires the user's explicit confirmation. The agent loop also asks the provider after every model call whether the usage data shows paid credit use (`credit_spend_detected`, M1). If so, every plan request pauses until the user resumes; the reply already paid for is kept. Tests: `test_s6_paid_credit_spend_pauses_every_plan_request`, the updated sign-in status test, and UI tests for the three credit states. |

| S7 | High | (Round 1) Connecting one Google app asked Google for Calendar and Gmail read access together, marked both connected and synced both, so a malicious model response could read Calendar data the user never connected. | **Fixed.** Google connections are per app. Connecting Gmail asks only for Gmail's read scope, and Calendar likewise. Each app is recorded as connected only when Google granted its own scopes. The background runner and "Sync now" sync only connected apps; the older `opendot google-auth` setup keeps working as before. Disconnecting one app keeps the other, and the refresh token is deleted when none is left. Tests: `test_connect_starts_read_only_with_pkce_and_finishes_through_the_callback`, `test_disconnecting_one_google_app_keeps_the_other`, `test_connections_include_a_google_app_that_never_synced`. |
| S8 | High | (Round 1) After the daemon stops, another local process can bind 127.0.0.1:8765 and serve script on the same origin, reading a bearer token kept in that origin's localStorage. | **Fixed.** The browser keeps only a session token, and session tokens exist only in the running daemon's memory. By the time anything else can hold the port, the stored token is already invalid. Test: `test_session_tokens_die_with_the_daemon`. |
| S9 | Medium | (Round 1) The Gmail drafts switch requested Calendar's write scope too and enabled both apps' write tools. | **Fixed.** Each app has its own write switch, write scope and tools: Gmail drafts (and the send proposal) for Gmail, events for Calendar. Turning on Gmail drafts asks Google only for `gmail.compose`. Tests: `test_write_opt_in_asks_google_for_write_scopes_then_allows_writes`, `test_s9_each_google_app_write_switch_offers_only_its_own_tools`, `test_connections_list_reports_health`. |
| S10 | High | (Round 2) A process holding the reclaimed port could serve a fake login page and capture the long-lived token when the user pasted it in to sign in again. | **Fixed.** No page asks for the access token any more. `opendot open` (CLI) runs the challenge exchange with the daemon (refusing an impostor), receives a single-use login code that expires in two minutes, and opens `/login#code=...`. The page trades the code for a session token and removes it from the address bar. A fake page can obtain at most an expired or spent code. Tests: `test_no_cookie_ever_and_no_page_carries_or_asks_for_the_token`, `test_one_time_login_codes_from_opendot_open`, `test_opendot_open_refuses_an_impostor`. |
| S11 | Medium | (Round 2) With the Gmail drafts switch on, the agent was offered `message_send_propose`, although the opt-in says OpenDot cannot send email in this version. | **Fixed.** `message_send_propose` is never offered to the agent in v0.1, and the agent's approval executor refuses to execute any `gmail_message_send` approval. Sending stays declared as reaching people, so it always asks once it returns in v0.2 with its own opt-in. Tests: `test_sending_is_declared_as_reaching_people_and_always_asks`, `test_s11_the_agent_never_executes_an_email_send`. |
| S12 | Medium | (Round 3) `opendot open` passed the one-time code to the browser in the launch URL, where another local user could read it from the process arguments and redeem it first; sessions also had no time limit. | **Fixed.** `opendot open` prints the code in the terminal only and opens a plain `/login`; the user types it. Codes have 60 bits of entropy, work once and expire after two minutes. Sessions expire after seven days and `/logout` revokes them in the daemon. An open chat WebSocket re-checks its session on every frame and event and every 15 seconds, and closes (1008) once the session expired or was revoked (round 4). Tests: `test_one_time_login_codes_from_opendot_open`, `test_sessions_expire_and_can_be_revoked`, `test_logout_revokes_the_session`, `test_an_open_websocket_closes_when_its_session_is_revoked`. |
| S13 | Medium | (Round 4) The ten-wrong-codes lockout let any local process clear the owner's pending codes and block browser sign-in. | **Fixed.** No lockout. Each code's 60 bits, single use and two-minute lifetime make guessing hopeless, and wrong guesses never affect real codes. Test: `test_wrong_guesses_never_block_the_owner`. |

Also found and fixed during M4, outside Sol's list:

- Reminders, routine results and the catch-up note were queued for `desktop:`/`ui:` destinations that nothing delivered. They now reach the "From your companion" conversation (`companion_inbox.py`).
- A flaky test exposed a real redaction bug: the credit-card pattern matched about 1 in 800 random memory ids (UUIDs), scrubbing them from the prompt. The redactor now leaves UUID record ids untouched (PR #9).
- A test once wrote a fake GitHub token into the developer's real keychain; it was removed, and every test now runs against an in-memory keyring (`tests/conftest.py`).

Final local run on the fix branch: 1447 daemon tests passed (6 skipped: POSIX-only checks on Windows; they run on Linux and macOS in CI), and the UI suite and builds passed.
